## 1. 总览

### 1.1 目标

把多平台（网页 / 微信 / 抖音 / B 站 / 小红书等）链接收入同一收藏库，尽量解析标题、封面、正文与媒体，供个人检索、阅读、标注与整理。

**工程约定**：链接解析、URL 规范化、媒体字段与防盗链等问题 **优先只改 backend**，让已上架 App 通过拉列表 / `reparse` / `refresh-video` 生效，避免「解析一改就要发版」。细则见 §4.9。

### 1.2 仓库结构

```
collection-app/
├── app/                 # Flutter iOS/Android 客户端
├── backend/             # Express + MySQL API + 静态落地页
├── extension/           # Chrome MV3 侧栏扩展（收藏/浏览为主）
├── docs/                # 产品与技术文档
└── .cursor/rules/       # Agent 视觉等约定
```

### 1.3 运行时拓扑

```
┌─────────────┐   JWT    ┌──────────────────┐
│ Flutter App │─────────►│ backend :3001    │──► MySQL `collection`
│ Chrome Ext  │          │ Express + parser │
└─────────────┘          └────────┬─────────┘
                                  │ 按需请求
                                  ▼
                         各内容源站 / 公开 API
                         （部分平台须客户端本机抓 HTML）
```

| 组件 | 技术 | 默认地址 |
| --- | --- | --- |
| App | Flutter 3.x / Dart SDK `^3.12.2` | 本地 API：`http://127.0.0.1:3001`（`ApiConfig`，可 `--dart-define=API_BASE_URL=`） |
| Backend | Node **23.6.0**、pnpm、Express 5、mysql2、cheerio | `0.0.0.0:3001` |
| Extension | Chrome MV3 | 配置里常见生产基址：`https://inkmind.xyz/collection`（以 `extension/config.js` 为准） |
| 静态站 | `backend/public/` | `/`、`/privacy`、`/support` |

> 生产域名在不同环境可能为 `conflux.wobufang.com` / `inkmind.xyz` 等，以实际部署与 `api_config` / 扩展配置为准。仓库内**无** Docker / GitHub Actions 部署脚本；线上多用手工部署 + PM2。

## 2. Backend

### 2.1 入口与路由

| 文件 | 作用 |
| --- | --- |
| `backend/src/index.js` | 启动；先 ping DB，失败仍 listen |
| `backend/src/app.js` | CORS、`express.json(8mb)`、静态 `public/`、挂路由、错误处理 |
| `backend/src/middleware/auth.js` | `requireAuth`：`Authorization: Bearer <accessJWT>` |

| Prefix | 说明 | 鉴权 |
| --- | --- | --- |
| `/api/health` | 健康检查 | 否 |
| `/api/auth` | 短信登录 / refresh / me / 注销 | 部分 |
| `/api/items` | 收藏 CRUD、解析、标注等 | 是 |
| `/api/folders` · `/api/tags` · `/api/system-filters` · `/api/home` | 分类与首页 | 是 |

### 2.2 配置（`src/config.js` + `.env`）

| 组 | 关键变量 |
| --- | --- |
| Server | `PORT`（默认 3001） |
| MySQL | `MYSQL_HOST/PORT/USER/PASSWORD/DATABASE` |
| JWT | `JWT_SECRET`、`JWT_ACCESS_EXPIRES`（默认 `7d`）、`REFRESH_EXPIRES_DAYS`（默认 30） |
| SMS 开发 | `SMS_DEV_MODE`（默认 true）、`SMS_DEV_CODE`（默认 `123456`） |
| App Store 审核白名单 | `SMS_REVIEW_PHONE`（默认 `15868843247`）、`SMS_REVIEW_CODE`（默认 `888888`） |
| 阿里云短信 | `ALIYUN_ACCESS_KEY_*`、`ALIYUN_SMS_SIGN_NAME`、`ALIYUN_SMS_TEMPLATE_CODE` |

开发模式可不发真实短信，固定验证码登录。生产环境 `SMS_DEV_MODE=false` 时，审核白名单手机号仍跳过阿里云短信，用 `SMS_REVIEW_CODE` 登录（供 App Review 使用）。

### 2.3 鉴权

1. `POST /api/auth/sms/send` → 发码（dev 写日志不发；prod 走阿里云号码认证 Dypnsapi）
2. `POST /api/auth/sms/login` → 校验 → 无用户则注册 → 发 access JWT + refresh
3. `POST /api/auth/refresh` → 轮换 refresh（旧 session `revoked_at`）
4. `DELETE /api/auth/account` → 注销（删账号及相关数据）

- Access：JWT `{ sub, phone }`
- Refresh：随机 hex，库内存 **SHA-256**（表 `user_sessions`）
- 实现：`services/authService.js`、`services/aliyunSms.js`

### 2.4 条目与两阶段解析

**创建** `POST /api/items`（`itemService.createItem`）：

1. `normalizeUrl`；专项解析后 **规范化 `canonical_url`** 等入库字段（见 §4.9）
2. 按 `canonical_url` 用户维度去重
3. `detectPlatform`；短超时 `fetchQuickMeta`（标题/封面等）
3. INSERT `status=pending`；缓存 HTML / 专项解析结果（约 5 min）
4. `enqueueParse` → 进程内队列 `parseQueue.js`（`setImmediate`，可日后换 Redis/Bull）

**正文解析** `runContentParse`：

| 情况 | 行为 |
| --- | --- |
| 适配器 `fetchMode=client` | 直接标 `NEED_CLIENT_FETCH`，等 App 本机抓页回传 |
| 云端可解析 | `parseFullContent` → 写 content / image_urls / video_url |
| 被墙 / 空正文 | `NEED_CLIENT_FETCH` 或 `failed` |

| API | 作用 |
| --- | --- |
| `POST /api/items/:id/reparse` | 重新入队解析（`resolveParseUrl` 优先带 id 的 URL） |
| `POST /api/items/:id/refresh-video` | 重跑专项/全文解析，刷新 `video_url` 与正文 `!v` |
| `POST /api/items/:id/parse-with-html` | 客户端提交源站 HTML |
| `GET …/parse-status` · `needs-client-fetch` | 轮询 / 待本机抓页列表 |

### 2.5 解析器框架

路径：`backend/src/services/parser/`

| 模块 | 职责 |
| --- | --- |
| `index.js` | `fetchQuickMeta` / `parseFullContent` 编排 |
| `adapters/registry.js` | 按 platform / `detectFromHtml` 选适配器 |
| `fetchHtml.js` | 服务端拉 HTML |
| `extractMeta.js` / `extractContent.js` | 元信息与正文；适配器优先，通用兜底 |
| `htmlText.js` | HTML → 阅读用富文本（见 §4） |

适配器两种能力（可并存）：

- **`fetchParsed(url)`**：不依赖空壳 HTML，直接打 API / 签名接口
- **`extractMeta` / `extractContent(html)`**：吃 HTML（含客户端回传）

`fetchMode`：

- `server`：云端解析
- `client`：云端常被拦，标 `NEED_CLIENT_FETCH`，等本机 HTML

### 2.7 URL 工具（`src/utils/url.js`）

| 函数 | 行为 |
| --- | --- |
| `normalizeUrl` | 去 tracking / utm；稳定 query；**infzm** → `/wap/content/{id}`；**xinhuaxmt** → `/vh*/share/{docid}?docid=` |

### 3.4 阅读与媒体

- 正文解析：`ArticleContentBlocks`（`article_content_blocks.dart`）
  - 图：`![alt](url)`（alt 可带 `宽x高`）
  - 视频：**单独一行** `!v[poster](playUrl)`；`playUrl` 可为 `https://…` 或 `qqvid:{vid}`
- 顶栏视频：`ItemVideoPlayer`；消费 API 返回的 `videoUrl`（B 站 bilivideo 等场景 iOS 可走 WebView）
- **播客/纯音频**（小宇宙、`m4a`/`mp3` 等）：阅读页级 `ReadingMediaController` + **just_audio**（无 Platform View），滚出视口与**息屏**可续播；iOS `UIBackgroundModes: audio`
- 真视频仍用 `video_player` / WebView；离屏可能被系统暂停
- 正文视频：消费 `!v[poster](playUrl)`；`playUrl` 为 `https://…` 或 **`qqvid:`**（由后端写入，见 §4.7）
- 图集：`isImageGallery` 时顶部轮播；普通文章图走正文，避免与轮播重复

**解析相关逻辑不放客户端**：平台怎么抓、URL 怎么规范、封面/正文/视频填哪个字段、短链怎么展开、直链过期怎么刷新——一律 backend 负责（§4.9）。App 只展示 API 字段并按通用协议消费（Referer、富文本、`qqvid:`）。

`CollectionItem` 关键字段：`url` / `canonicalUrl` / `platform` / `title` / `content` / `summary` / `coverImageUrl` / `imageUrls` / `videoUrl` / `status` / `note` / 夹与星标等；派生 `sourcePageUrl`。

## 4. 解析与阅读页显示规则

核心约定：**图集走字段 `imageUrls`（顶部轮播，正文不再插这些图）；长文走正文 Markdown 插图 `![]()`，此时 `imageUrls` 必须为空。** 阅读页**不看平台名**，只看这两个字段 + `videoUrl`。

实现：后端各 adapter 填字段；App `CollectionItem.isImageGallery` / `ItemReadingPage` 决定版式。

### 4.1 两条存储路径（解析时必须二选一）

| 类型 | `imageUrls` | `content` 里的图 | 阅读页 |
| --- | --- | --- | --- |
| **图集 / 短帖**（朋友圈式多图 + 短文案） | 填图 URL 列表（最多约 30 张） | **不要**写 `![]()` | 标题下 **轮播**，下方纯文字 |
| **长文 / 图文混排** | **必须 `[]`** | 图写成 `![alt](url)`，插在对应段落 | **无轮播**，图跟在正文位置 |
| **独立视频帖** | 一般空（封面放 `coverImageUrl`） | 通常无 `!v` | 标题下 **顶栏播放器**（`videoUrl`） |
| **文中内嵌视频** | 空 | 整行 `!v[poster](playUrl)` | **无顶栏播放器**，播放器插在正文该行 |

`coverImageUrl`：列表/详情封面、顶栏视频海报。**不会**因为有封面就在阅读页再出一张大图；封面要出现在阅读流里，要么进 `imageUrls`（图集），要么进正文 `![]()`。

### 4.2 阅读页判定（App，`item_models.dart`）

**是否图集轮播** `isImageGallery`（须同时满足）：

1. `imageUrls` 非空  
2. `hasVideo == false`（有顶栏视频则不当图集）  
3. 正文 **没有** `![]()` 也没有 `!v[]()`（正则 `!v?\[[^\]]*\]\([^)\s]+\)`）

任一不满足 → **不轮播**。因此：长文即使误带了 `imageUrls`，只要正文已有 `![]()`，仍按插图文处理、不轮播。

**是否顶栏视频** `hasVideo`：

- `videoUrl` 非空才可能为 true  
- **例外（抖音）**：URL 含 `/note/` 或 `/slides/` → 强制不当视频；或 platform=douyin 且 `imageUrls` 非空 → 不当视频（图文笔记优先）

**正文是否内嵌视频** `hasInlineVideos`：正文能拆出 `ArticleVideoBlock`（含 `!v` 行，或封面 URL 能抽出腾讯 vid 而升级成播放器）。

### 4.3 阅读页版式（`item_reading_page.dart`）

从上到下：

1. 标题、日期/来源  
2. **媒体区（互斥）**  
   - 若 `hasVideo && 正文无内嵌视频` → 顶栏 `ItemVideoPlayer`（`videoUrl`）  
   - 否则若 `isImageGallery` → `ItemImageGallery` 轮播（只用 `imageUrls`，不用封面兜底）  
   - 两者都不满足 → 无顶部媒体块  
3. **正文**  
   - 含富文本标记（图 / `!v` / 标题 / `**` / `{{` 等）→ 按块渲染：文字、标题、**插图**、**文中播放器**  
   - 否则纯文字 + 标注  

因此：**轮播和文中插图不会同时出现**（图集正文禁止 `![]`；长文 `imageUrls` 为空）。  
**顶栏视频和文中 `!v` 也不会同时出现**（有内嵌则不再用 `videoUrl` 顶栏）。

详情页预览（非阅读页）：图集出轮播；普通文章只展示 **一张** `coverImageUrl`（没有则 `displayImages` 第一张）。

### 4.4 各平台解析：图往哪放

| 平台 | 图集轮播（填 `imageUrls`，正文不插图） | 文中插图（`imageUrls=[]`，`htmlToRichText`） |
| --- | --- | --- |
| **微信 weixin** | `item_show_type=8` 图文帖：抽图进 `imageUrls`，正文只用纯文字/短 caption | 普通文章 `#js_content`：图留在 HTML → `![]()` |
| **抖音 douyin** | 图文/slides/note：`imageUrls`=图集；`/note/`、`/slides/` 或图多于 1 张时 **清空 `videoUrl`**。纯视频页客户端 **不把封面塞进 `imageUrls`** | 不做长文插图 |
| **快手 kuaishou** | 非 VIDEO：atlas/`imageUrls`/封面进列表 | 视频帖：`imageUrls=[]`，只用 `videoUrl` |
| **小红书 xiaohongshu** | 笔记 `imageList` → `imageUrls`，desc 为纯文本 | 视频笔记：有 `videoUrl` 则阅读页走顶栏视频（`hasVideo` 为真则不轮播）；封面可能仍在 `imageUrls` 但不展示为轮播 |
| **微博 weibo** / **即刻 jike** / **视频号 channels** | 帖子配图进 `imageUrls`，文案为纯文本 | — |
| **头条 toutiao** / **腾讯新闻 qqnews** / **新浪 sina** / **人民日报 people** / **澎湃 thepaper** / **南周 infzm** / **新华社 xinhuaxmt** / **小宇宙 xiaoyuzhou** / **36氪 kr36** / **通用 web** | 一律 `imageUrls=[]` | 正文 HTML 转 `![]()`；位置跟原文 `<img>`（小宇宙为 Shownotes） |

B 站 `fetchBilibili` 会把封面写入 `imageUrls`；因同时有 `videoUrl`，`hasVideo` 为真 → **不轮播**，封面只当播放器海报。

通用 `extractGenericContent`：从 `article` / `.article-content` 等容器 `htmlToRichText`，图进正文，**不填** `imageUrls`（除非该平台 adapter 另给）。

### 4.5 视频放哪

| 情况 | `videoUrl` | 正文 `!v` | 阅读页 |
| --- | --- | --- | --- |
| 抖音/快手/B 站/小红书视频/视频号等「一条视频」；**小宇宙单集音频（m4a）** | 填直链（含音频 URL） | 一般不写 | 顶栏播放器 |
| 头条 / 腾讯新闻 / 新浪 / 人民日报 / 澎湃等「文中有视频」 | **置空**（有内嵌则不要顶栏） | 在对应位置写 `!v[海报](播放地址)` | 正文内嵌播放器 |
| 腾讯新闻 | 空 | `!v[海报](qqvid:{vid})`，手机再解直链 | 文中播放器 |
| 新华社 | 仅真实 `videourl` | 有则 `!v`；**禁止**朗读 `audioUrl` | 有视频才内嵌 |

顶栏播放器失效：B 站 / 头条 / 腾讯 / 新浪等可 `refresh-video`（**解析问题优先 backend 修**，§4.9）。腾讯 `qqvid:` 由客户端通用解析器消费。

生产环境解不出直链时，曾把腾讯封面写成普通 `![]()`；阅读页若从封面 CDN 抽出 vid，会把该图 **升级成播放器**（`article_content_blocks.dart`）。

### 4.6 富文本语法（`htmlText.js`）

| 语法 | 含义 |
| --- | --- |
| 段落换行 | 普通文本 |
| `#`～`####` | 标题 |
| `**…**` / `*…*` | 加粗 / 斜体 |
| `{{18|…}}` | 行内偏大字号 |
| `![…](url)` 或 `![宽x高](url)` | **文中插图** |
| `!v[poster](url)` | **文中视频**（必须单独一行） |

### 4.7 腾讯新闻视频（`qqnews`）

- 问题：服务端 `getinfo` 得到的 mp4 **vkey 易过期**；DOM 常无 `VIDEO_` 占位，视频在 `getSimpleNews` / HTML 内 `vid`
- 现行策略：正文统一写 **`!v[poster](qqvid:{vid})`**，由手机端解最新直链；无占位时 `prependVideos` 把视频插到正文前
- App：`QqVideoResolver`；失败可 `refresh-video`

### 4.8 新华社（`xinhuaxmt`）

- 分享页 SPA 空壳；API：`https://h.xinhuaxmt.com/1017/n/newsapi/h5/news-detail/{docid}?sign=`
- 签名：`Key=sm3("H5")`，`Signature=sm3(Key&Timestamp&Token&Request=…)`（DeviceAccessId 空时用短 payload）
- **不写入** `audioUrl` 朗读音频；仅图文 + 真实 `videourl`（若有）

### 4.9 链接解析与「少发版」约定

**原则**：凡与「链接怎么解析、存什么 URL、媒体能不能拉下来」相关的问题，**优先只改 backend**（适配器、`url.js`、`itemService`、修库脚本、`reparse` / `refresh-video`），让已上架 App 拉列表或重解析即生效。**不要在客户端堆平台表、域名规则或解析兜底**——否则源站/CDN 一变就要发版。

#### 属于「解析链路」、应后端修的范围

| 类别 | 典型问题 | 后端手段 |
| --- | --- | --- |
| **URL 身份** | 短链未展开、hash 丢 id、canonical 不能去重 | `normalizeUrl` / `resolveParseUrl`；适配器 `pageUrl`；`normalizeBilibiliCanonical` 等 |
| **平台识别** | 新域名、分享链 host 不对 | `detectPlatform`；`itemService` 中文别名 |
| **元信息与正文** | 标题空、封面错、正文缺图、图集/文中图分工错 | 改对应 `adapters/*`、`extractMeta` / `extractContent`、`htmlText`（§4.3–4.6） |
| **视频/音频 URL** | 直链过期、API 字段变更、该顶栏还是文中 `!v` | 适配器重抓；`video_url` 置空 + `!v`；腾讯 **`qqvid:`** 稳定 id（§4.7）；`refresh-video` |
| **媒体防盗链** | 封面 403、CDN 校验 Referer | **规范 canonical** 为 CDN 认可的源站页；App 仅用 `canonicalUrl` origin 作 Referer（下节） |
| **存量脏数据** | 历史条目字段错、旧规则入库 | `mapItem` 读出兜底；`pnpm fix:*` 一次性脚本 |
| **解析失败** | 云端被拦、空壳 HTML | `NEED_CLIENT_FETCH` + `parse-with-html`（客户端只回传 HTML，**不做二次解析规则**） |

#### 客户端职责（刻意保持「哑消费」）

- 展示 API：`title` / `content` / `coverImageUrl` / `imageUrls` / `videoUrl` / `platform` 等；**不根据 platform 决定「该怎么解析这条链」**。
- 拉图/拉音视频：`Referer = sourcePageUrl` 的 **站点 origin**（优先 `canonicalUrl`）。**不维护**各平台 CDN Referer 表（`media_http_headers.dart`）。
- 正文视频：识别通用语法 `!v[poster](playUrl)`；`qqvid:` 由 `QqVideoResolver` 解直链——**vid 由后端写入正文**，客户端不扫 DOM 补 vid。
- 本机抓页：仅 `client` 模式把 HTML 回传；解析规则仍在服务端适配器。
- 用户触发的 **reparse** / **refresh-video** 调 API，不在本地重跑平台逻辑。

因此：**服务端返回什么 canonical、content、video_url，客户端就信什么**；解析 bug 的修复面应在「改库 + 改 API 输出」，而非改 App 判断。

#### `canonical_url` 应表示什么

| 应表示 | 不应仅表示 |
| --- | --- |
| 内容的稳定身份（去重、搜索） | 用户粘贴的短链形态（如 `b23.tv/xxx`） |
| CDN / 防盗链认可的页面 origin（若该平台校验 Referer） | 跳转中间页、带大量 tracking 的原始 URL |

专项解析（`fetchMode=server`）适配器应返回 **`pageUrl`**（规范 canonical 页），写入库并在 API 返回；示例：B 站 `https://www.bilibili.com/video/BV…`，而非 `b23.tv`。

#### 后端必须做的三层（新平台 / 源站变更时的默认动作）

| 层 | 时机 | 作用 |
| --- | --- | --- |
| **解析规范化** | `createItem` / `runContentParse` / `refreshItemVideo` | 新入库、重解析时字段写成正确形态 |
| **读出兜底** | `mapItem` 返回 JSON 前 | 存量脏数据读时修正（如 B 站 canonical 从 `url` 抽 BV） |
| **一次性脚本** | 上线后修库 | 如 `pnpm fix:bilibili-canonical`；避免等用户重收藏 |

新增/变更平台 checklist：

1. 短链 / 分享链是否需展开？`normalizeUrl` / `resolveParseUrl` 会不会丢 id（如 infzm hash）？
2. 标题、封面、正文、图集 vs 文中图、顶栏 vs `!v` 是否按 §4.3–4.5 填对字段？
3. `video_url` / 正文播放地址是否易过期？是否用 `qqvid:` 等稳定 id + `refresh-video`？
4. CDN 是否校验 Referer？canonical 的 origin 是否等于 CDN 要求的 Referer？
5. 能否 **只改 backend** 验证？（改适配器 / 改库 / `reparse`，旧 App 拉详情即生效）

#### 案例

**B 站 `b23.tv`（Referer + canonical，2026-08-25）**

| 项 | 说明 |
| --- | --- |
| 现象 | 封面 403、视频不播 |
| 根因 | DB 存 `canonical_url=https://b23.tv/…` → App Referer 为 `https://b23.tv/`；B 站 CDN **只认** `https://www.bilibili.com/` |
| 不发版修复 | 规范 `canonical_url`；`mapItem` 兜底；`pnpm fix:bilibili-canonical` |
| 教训 | 曾在客户端强制 B 站 Referer / WebView——能修但违背本节约定的「解析规则在后端」 |

**腾讯新闻 `qqvid:`（视频 URL + 正文协议）**

| 项 | 说明 |
| --- | --- |
| 现象 | 服务端 mp4 vkey 过期，顶栏/内嵌播不了 |
| 不发版修复 | 正文写 `!v[poster](qqvid:{vid})`，由既有 `QqVideoResolver` 解最新直链；`refresh-video` 重抓 |
| 教训 | 长期存带 vkey 的 mp4 在 `video_url` → 每次 CDN 规则变都要发版；稳定 id + 通用协议可后端迭代 |

**澎湃 infzm（URL 身份）**

| 项 | 说明 |
| --- | --- |
| 现象 | 规范化后 hash 丢 content id，解析失败 |
| 不发版修复 | `normalizeUrl` 改为 path `/wap/content/{id}` + `resolveParseUrl` 回退 raw |
| 教训 | URL 规范化是解析链路一环，必须在 `url.js` / 服务端修，不能靠 App 特判 |

#### 何时仍可能需要发版

- **播放技术**变化：必须 WebView、新解密、新传输协议，且无法通过「改 URL / 改正文协议 / 代理媒体」解决
- **新 UI / 新能力**：文稿、交互、布局，与解析字段无关
- **新客户端能力**：例如首次引入 `qqvid:` 解析器——之后同类问题仍应后端写 `qqvid:`，而非 App 加平台分支
- 服务端统一媒体代理（API 域名出流）可进一步减少发版，带宽与实现成本另议

实现索引：`parser/adapters/*`、`url.js`、`itemService`（`mapItem` / `createItem` / `runContentParse`）、`reparse` / `refresh-video` API；App 侧 `media_http_headers.dart`、`article_content_blocks.dart`、`qq_video_resolve.dart` 仅消费通用约定。

## 7. 已知坑与设计决策（速查）

| 主题 | 说明 |
| --- | --- |
