# 付费规划（收藏家 / Conflux）

> 状态：用量 + 订阅 + 触顶 + **iOS IAP 校验**已实现；ASC 商品与密钥需配置后可用  
> 更新日期：2026-08-31

## 1. 原则

| 能力 | 策略 |
| --- | --- |
| 收藏、**解析**、阅读、搜索、手动标签、系统分类 | **永久免费**，解析不设墙、不限次 |
| 转写（ASR） | 每月免费**分钟**额度；超额需订阅 |
| AI（标签建议 + 思维导图） | 按模型实际消耗 **token** 计月额度（**共用一池**）；超额需订阅 |

已生成内容（文稿、脑图、已采纳标签）**始终可查看**；额度只限制**新的消耗型调用**。

## 2. 订阅形态

- 初期只做一档：**Pro**（月付 + 年付折扣）
- 免费用户与 Pro 用户：**解析与基础能力完全一致**
- Pro：转写（分钟）与 AI（token）的**月额度更高**

额度数字待有真实用量后再定；实现前先做用量埋点（见 §6）。

## 3. 计量维度

### 3.1 转写（按分钟）

- **计量单位：音频/视频时长（分钟）**，与阿里云 ASR 成本对齐
- 以**转写成功**后确认的媒体时长入账（优先用 ASR/探测得到的 `durationSec`）
- **按实际时长计**：不足 1 分钟也按真实秒数折算分钟（例如 30 秒 = 0.5 分钟），**不设「最低扣 1 分钟」**
- 实现上可用「秒」累加，对用户展示为分钟（可一位小数）
- AI 标签 / 脑图触发的**自动先转写**同样按实际时长扣除，并在提交识别前用探测时长做严格预估触顶
- **失败不扣**；同一段「已有成功文稿拒绝重复转写」不扣
- 额度展示示例：「本月转写还剩 42.5 分钟」
- 严格预估：剩余不足以覆盖本段时长时提示「本段转写约需 X 分钟，本月剩余 Y 分钟不足」

### 3.2 AI（标签 + 思维导图，共用 token）

- 计量单位：**模型返回的 `total_tokens`**（prompt + completion）；标签与脑图写入同一 `kind=ai`
- **计入**：成功生成、以及标签「暂无新建议」(empty) 等已实际调模型的结果
- **不计**：采纳 / 忽略、查看结果、状态轮询、生成失败（未成功落账）
- 若生成前自动转写：转写扣转写额度，AI 成功后再扣 token
- 触顶：发起前若本月 AI 剩余 token 不足以覆盖**预估消耗**则拦截；成功后按真实 token 入账
- 展示示例：「本月 AI 还剩 12.5万 / 20万 token」

转写严格预估：媒体时长探测完成后、提交 ASR 前，若预估秒数 > 剩余分钟则失败（不提交识别）；AI 路径先转写时同样适用。

### 3.3 重新生成与用户方向（产品）

- **首次生成**：一键即可，不强制填写方向
- **重新生成**：弹层提供可选输入框，用户可写期望方向（可空）；有内容则写入模型 prompt
- 目的：重生成是「按意图再跑一版」，而非盲抽；减轻「AI 质量靠用户多付费」的不公平感
- 额度：每次成功调模型按实际 token 扣除（长文稿脑图通常更贵）

## 4. 触顶体验

- 入口保持可见
- 触发时提示：转写示例「本月转写分钟已用完，订阅后可继续」；AI 示例「本月 AI 额度已用完，订阅后可继续」
- 引导订阅页；取消则不发起请求

## 5. 支付与合规

- iOS：**In-App Purchase**（自动续期订阅：月 / 年）
  - App：`in_app_purchase` → StoreKit 购买 / 恢复购买
  - 后端：`POST /api/billing/apple/verify` 用 App Store Server API 校验交易后写 `subscriptions`
  - 续期 / 退款：`POST /api/billing/apple/notifications`（Server Notifications V2）
  - 商品 id 默认：`com.bufang.supercollection.monthly` / `.yearly`（可用环境变量覆盖）
- Android：可微信 / 支付宝（及必要时 IAP）— **未接**
- **订阅与额度以后端为准**；客户端只展示剩余与状态

## 6. 落地顺序

1. ✅ 用量记账（**转写分钟**、**AI token**）+ `GET /api/usage`；设置页展示本月用量

3. ✅ 订阅表 `subscriptions` + `GET /api/usage` 返回真实 `plan`；触顶 402；App 引导升级页

## 8. 偏好学习（用更少次数贴近用户）

目标：把用户填写的「期望方向」沉淀为偏好，使**首次生成更准、重生成更少**。不做模型微调，用「记忆 + 注入 prompt」。

### 8.1 记什么

| 事件 | 说明 |
| --- | --- |
| 显式方向 | 用户在重新生成（或将来首次可选）时填写的 `direction` |
| 采纳信号（标签） | 用户采纳建议标签 → 强化该次方向（若有） |

表：`ai_preference_events`（用户、条目、`kind`=tags|mindmap、方向原文、可选 outcome）。

### 8.2 怎么用

- **有本次方向**：优先遵循本次；历史偏好仅作弱参考  
- **无本次方向**（含首次生成）：注入该用户该类型**近期去重后的偏好**（默认最多 5 条）  
- 标签 / 脑图偏好**分开**记忆

### 8.3 边界

- 仅存用户主动填写的方向，不存全文内容到偏好表  
- 后续可提供「清除 AI 偏好」；单次方向始终覆盖历史  
- 与额度正交：学习减少必要调用次数，计费仍按实际 token
